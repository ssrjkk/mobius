# ADR 009: DeviceProfileLoader — config-driven device capabilities (YAML)

**Статус:** Accepted
**Дата:** 2026-04-24
**Автор:** Ситников Сергей (ssrjkk)

## Контекст

`pixel_6_api33()` / `iphone_15_ios17()` в `capabilities.py` хардкодят
устройства как Python-функции. В реальном CI с матрицей из 10+
конфигураций (разные API level, разные производители устройств для
device cloud) добавление каждой новой конфигурации через правку Python
кода неудобно и требует code review на то, что по сути является данными.

## Найдено при разработке

`mobius/driver/device_profiles.py` (`DeviceProfileLoader`) обнаружен
через систематическую проверку `vulture --min-confidence 60` по всему
`mobius/` — **второй** orphaned-файл в этой сессии (первый: ADR-008,
`retry_config.py`). Оба потеряны одним и тем же образом — написаны в
части беседы, которая была прервана сбросом контейнера, и не попали в
git до следующего восстановления из последнего сохранённого архива.

В отличие от ADR-008, здесь код был логически корректен (проверено
эмпирически — YAML/JSON парсинг, Android/iOS профили, `get()`/`get_all()`
все работали с первого прогона). Единственный дефект: error message в
`_load()` ссылался на `docs/device_profiles_example.yaml` — файл,
который никогда не существовал. Пользователь, получивший
`FileNotFoundError`, был бы отправлен искать несуществующий пример.

## Решение

1. Создан `devices/ci_matrix_example.yaml` — реальный, рабочий пример
   с 3 профилями (2 Android разных API level + 1 iOS), демонстрирующий
   формат.
2. Error message исправлен на реальный путь.
3. `DeviceProfileLoader` добавлен в публичный API (`mobius.DeviceProfileLoader`).

## Обоснование дизайна (уже заложено в найденном коде, подтверждено)

- Формат `{"profiles": {name: {...capabilities...}}}` — плоский словарь
  по имени, не список — упрощает `loader.get("pixel_6_api33")` без
  необходимости линейного поиска.
- `AutomationName` вычисляется автоматически из `platform`, если не
  указан явно (`UiAutomator2` для Android, `XCUITest` для iOS) —
  уменьшает boilerplate в YAML для типичного случая.
- Поддержка и YAML, и JSON (как в `AppConfig`, ADR-002) — консистентность
  с уже установленным паттерном в проекте.

## Связь с ADR-002

Это НЕ дублирование `AppConfig`/`ConfigDrivenScreen` (ADR-002) — разные
задачи:
- `AppConfig` (`apps/*.yaml`) — конфиг ОДНОГО приложения: capabilities
  + именованные ЛОКАТОРЫ для config-driven Screen Object тестирования.
- `DeviceProfileLoader` (`devices/*.yaml`) — конфиг МНОЖЕСТВА устройств
  (capabilities без локаторов) — для выбора точки CI-матрицы устройств,
  независимо от того, какое приложение/экран тестируется.

Оба инструмента можно комбинировать: `DeviceProfileLoader` выбирает
устройство, `AppConfig` — приложение и его локаторы на этом устройстве.

## Урок процесса (повтор из ADR-008, теперь дважды подтверждён)

Систематическая проверка dead-code detector'ом (`vulture`) поймала
ВТОРОЙ случай orphaned-кода за сессию, который ручной осмотр не поймал
бы без специального повода. Стоит гонять `vulture mobius/
--min-confidence 60` периодически как часть ревизии, не только когда
что-то уже заподозрено — именно так был найден этот файл: не по жалобе
пользователя, а по систематической проверке "что ещё может быть
потеряно после стольких сбросов контейнера".

## Дополнение (финальная проверка, тот же день)

При финальной сквозной проверке всего проекта после ЕЩЁ ОДНОГО сброса
контейнера обнаружилось, что интеграция `DeviceProfileLoader` (публичный
API, пример-файл, фикс error message, тесты) не сохранилась в последнем
восстановленном архиве — восстановлена заново в рамках финальной
верификации. Сам этот факт — лишнее подтверждение урока выше: находки
такого рода легко теряются между сессиями и должны перепроверяться
систематически, а не приниматься на веру по памяти о прошлой работе.

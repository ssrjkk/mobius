# ADR 003: WARNING vs DEBUG в структурированном логировании

**Статус:** Accepted
**Дата:** 2026-04-15
**Автор:** Ситников Сергей (ssrjkk)

## Контекст

Universal-слой (`device.py`, `alerts.py`, `network.py`, и т.д.) построен
на best-effort паттерне: если конкретная Appium команда не поддерживается
драйвером/платформой, метод возвращает `False`/`None`/`[]` вместо падения
теста. Изначально это делалось через `except Exception: return False`
без единой строчки лога — 61 такое место по всему коду.

## Проблема

Команда в реальном CI получала молчаливый провал (`device
.rotate_to_landscape()` вернул `False`) без единой подсказки, что
конкретно пошло не так — часами дебажили бы код чтобы понять, что
Appium команда просто не поддерживается этим драйвером/эмулятором.

## Решение

Каждый `except Exception` теперь логирует, но на РАЗНЫХ уровнях:

- **WARNING** — когда что-то РЕАЛЬНО не сработало и это, вероятно,
  указывает на проблему конфигурации/окружения (`device.reset_app()`
  не смог остановить приложение, `NetworkSimulator._apply()` не
  поддерживается эмулятором, `PermissionsManager.grant()` упал).
- **DEBUG** — когда `False`/`None` — ОЖИДАЕМЫЙ нормальный исход, не
  ошибка (`is_element_present()` не нашёл элемент на негативном тесте,
  `is_appium_available()` вернул `False` при unit-only прогоне без
  сервера, `is_displayed` на отсутствующем элементе).

## Обоснование

Если бы всё логировалось на WARNING, здоровый прогон тестов заваливал
бы CI-логи ложными предупреждениями на каждый негативный тест
(`test_login_wrong_password` — это ПРАВИЛЬНО что элемент ошибки
появился, а не "проблема"). Разработчик перестал бы обращать внимание
на WARNING вообще — то есть логирование стало бы бесполезным ИЗ-ЗА
избыточности, а не из-за отсутствия.

## Последствия

- `tests/unit/test_logging_infrastructure.py` содержит ОБРАТНУЮ
  проверку: `is_displayed=False` НЕ должен логироваться как WARNING.
  Это защита от будущего регресса, когда кто-то по привычке добавит
  WARNING туда, где на самом деле нормальный control flow.
- Граница WARNING/DEBUG — вопрос суждения, не формальное правило.
  Критерий который применялся: "если бы это увидел дежурный инженер
  в 3 часа ночи, стал бы он открывать тикет?" — да → WARNING,
  нет ("а, ну там просто элемента не было") → DEBUG.

## Альтернативы рассмотрены

- Один уровень (всё WARNING): отклонено — see Проблема выше.
- ERROR для сбоев: избыточно, эти fallback'и НЕ прерывают выполнение
  теста, WARNING точнее отражает "operation degraded, но продолжаем".

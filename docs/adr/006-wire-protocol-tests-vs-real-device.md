# ADR 006: Wire-protocol тесты вместо real-device тестов в CI

**Статус:** Accepted (временная мера, не финальное решение)
**Дата:** 2026-04-18
**Автор:** Ситников Сергей (ssrjkk)

## Контекст

Framework предназначен для тестирования реальных Android/iOS приложений
через Appium. До этого ADR ВСЕ тесты (498+) были одного из двух типов:
- Unit: `MagicMock()` вместо `driver`
- API: `respx` моки вместо реального HTTP к dummyjson.com

## Проблема

Ни одна строчка Appium wire-протокола ни разу не была исполнена
по-настоящему. `create_driver()` и вся цепочка
`Gestures`/`DeviceActions`/`UniversalFinder` проверялись только на
уровне "код не падает при вызове мок-объекта" — категориально другая
проверка, чем "framework реально умеет управлять телефоном".

Прямое следствие: баг ADR-001 (`desired_capabilities`) существовал
незамеченным, потому что `create_driver()` был помечен `pragma: no
cover` — единственная причина по которой этот класс багов вообще
существовал в кодовой базе.

Среда разработки (sandboxed контейнер) физически не может запустить
Android эмулятор или iOS Simulator: нет Android SDK, нет
виртуализации на уровне ОС для запуска AVD, сеть режет доступ к
CDN с бинарниками (APK/эмулятор образы).

## Решение

`tests/wire_protocol/` — минимальный HTTP-сервер
(`http.server.ThreadingHTTPServer`), реализующий W3C WebDriver protocol
ровно настолько, чтобы Appium-Python-Client создал реальную сессию и
отправил реальные HTTP-команды. Framework код реально сериализует JSON,
реально открывает TCP-соединение, urllib3 реально делает HTTP-запрос —
единственное что не реально, это отсутствие настоящего Android/iOS за
сервером.

## Обоснование

Это СИЛЬНЕЕ чем mock (проверяет реальный транспортный слой
Appium-Python-Client, реальную JSON-сериализацию, реальную W3C
envelope-структуру), но СЛАБЕЕ чем реальное устройство (не проверяет,
что фактическое приложение отреагирует на команду правильно —
fake-сервер отвечает заранее прописанным правдоподобным JSON независимо
от реальной семантики команды).

Конкретное найденное через этот механизм: `DeviceActions.press_back()`
на самом деле отправляет `execute_script('mobile: pressKey', {keycode:
4})`, а не отдельный WebDriver endpoint — этот факт о реальном
поведении Appium-Python-Client не был известен заранее, обнаружен
именно через инспекцию реального трафика на fake-сервере.

## Что это НЕ решает (честно, открыто)

- НЕ проверяет что реальное Android-приложение корректно ответит на
  `mobile: changePermissions` или на W3C Actions swipe-жест — это
  зависит от реализации конкретного приложения и версии Appium-сервера
  на другом конце, wire-protocol тесты этого принципиально не видят.
- НЕ заменяет полноценный E2E прогон на CI с реальным Android
  эмулятором (`tests/ui/`, `.github/workflows/ci.yml` job
  `ui-android`) — тот слой существует, написан, но:
  - **никогда не был выполнен от начала до конца** в GitHub Actions
    (YAML написан и синтаксически провалидирован, но не прогнан на
    реальном runner'е — тот же класс риска что ADR-001, до
    подтверждения реальным запуском доверять нельзя полностью)
  - зависит от APK референсного (устаревшего) SUT — см. ADR-005

## Последствия / открытые задачи

- [ ] Прогнать `.github/workflows/ci.yml` на реальном GitHub Actions
      runner хотя бы один раз end-to-end, зафиксировать результат
- [ ] После миграции на актуальный SUT (ADR-005) — подтвердить что
      `tests/ui/` реально проходит против реального эмулятора, не
      только "auto-skip если Appium недоступен" (текущее поведение
      локально/в этой среде разработки)

## Альтернативы рассмотрены

- Docker-контейнер с headless Android эмулятором внутри этой sandbox
  среды: невозможно — требует KVM/hardware virtualization, недоступно
  в контейнеризированной среде без привилегированного доступа.
- Пропустить этот слой полностью, оставить только mock-тесты: отклонено
  — именно отсутствие этого слоя дало пройти багу ADR-001 незамеченным.
